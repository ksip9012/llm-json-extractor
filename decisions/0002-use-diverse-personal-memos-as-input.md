# 0002. 入力データに「多様な形式の短い個人メモ」を採用する

- Status: Accepted
- Date: 2026-09-27

## Context
Step1-B は Step1 シリーズの最終段階で、「スキーマも LLM に考えさせ、自由入力を
JSON 化する」ことが主題。Step1-A1・A2 と同じ題材（ファイル名の構造化）を
使い回す案もあったが、ファイル名は元々スキーマが一意に決まる題材であり、
「スキーマ自体を LLM に設計させる」という Step1-B 固有の価値が出にくい。

## Decision
入力データには、種類の異なる複数の短い個人メモ（買い物リスト・会議メモ・
日記・TODO の走り書きなど）を採用する。メモの種類によって最適な JSON 構造が
異なるため、LLM がスキーマを状況に応じて設計する必然性が生まれる。

Step1-A1 の [0003](https://github.com/ksip9012/json-schema-mapper/blob/main/decisions/0003-use-folder-file-list.md)
と同様、実際の個人メモは使わず、`fixtures/` にはダミーのメモを用意する。

## Consequences
- メモの種類ごとに出力 JSON の構造が変わるため、Step1-A1・A2 のような
  単一の `schema.json` に対する `jsonschema.validate()` は使えない。
  「LLM が出力した JSON がそもそも妥当な JSON か」「その入力に対して
  スキーマ自体が妥当か」をどう検証するかは、実装着手時に別 ADR で決める
- ダミーメモの作成コストが発生する（Step1-A1・A2 のようにファイル名だけで
  題材を用意することはできない）
- LLM プロバイダ・認証方式など、その他の技術的な論点は本 ADR では決めず、
  実装を進める中で必要になったタイミングで都度 ADR 化する
